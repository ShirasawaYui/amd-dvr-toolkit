# AMD DVR Toolkit

> Fix toolkit for the AMD Adrenalin "record button does nothing" bug (DVR scene-conversion silent failure).
> AMD 桌面录制/即时重放「点击无反应」的根因分析与修复工具包。

本仓库只包含脚本与文档，**不包含任何 AMD 官方二进制文件**（原版备份由脚本在首次运行时自动生成）。

## 一、问题现象

点击录制按钮后**毫无反应**：没有报错、没有文件落盘、界面上什么都不会发生。重启电脑有时能好一阵，之后又复发——同一套操作，成败看起来像"玄学"。

引擎日志（`%LOCALAPPDATA%\AMD\CN\dvrlog*.txt`）里能看到签名错误串：

```
Failed to send scene conversion to CN
```

（该错误串全网零命中，属 AMD 未公开的内部错误。）

⚠ 引擎日志默认**不生成**：`dvrlog` 只在注册表 `HKCU\SOFTWARE\AMD\DVR\LOG` 值**存在**时写（=1 或 =0 都写，值整个缺失则完全不写）。需要取证时先用「切换DVR日志开关.cmd」开启日志（见第九节）。

注意：还有另一种表象完全相同、但日志里**没有任何** `WMCN_` / `Failed` 行的成因（音频枚举导致引擎僵死），判据见第九节。

## 二、根因（已实测确认）

1. DVR 引擎（`AMDRSServ.exe`）每次点击录制时，需要找到 AMD 软件界面（CN，`RadeonSoftware.exe`）的 `CNEventWindowClass` 主窗口，发送一次「场景转换」消息后才开始录制。
2. 找窗口的方式是 `EnumWindows` 枚举全部窗口 + `GetClassNameW` 读取每个窗口的类名。
3. 该调用申请的类名缓冲区是 **520 字符（1040 字节）**，而事发线程栈上自缓冲区起只剩 **1024 字节**可用 → 请求越出线程栈顶 **16 字节** → user32 对整段目标范围的可写校验失败（`ERROR_NOACCESS` / 998）→ **所有窗口的类名都读不到** → 找不到目标窗口 → 静默放弃。
4. 余量只有 16 字节，且随线程调用链深度波动，所以成败是概率性的——重启有时能好一阵，有时不行。

## 三、修复原理

两处**等长改写**（文件大小不变、数字签名必然失效，因此两步必须配套）：

| 位置 | 原始 | 修复后 | 作用 |
| --- | --- | --- | --- |
| `AMDRSServ.exe` 文件偏移 **按构建**：`.02`–`.16` = `0x3686B`，`.29.02` = `0x3669B` | `08 02`（0x208 = 520） | `00 01`（0x100 = 256） | 类名读取请求缩到安全长度（真实类名最长几十字符，256 足够） |
| exe 内嵌清单 | `uiAccess="true"` | `uiAccess="false"` | 补丁破坏签名后，声明 uiAccess=true 的程序会被 Windows 拒绝启动；改 false 后正常启动 |

修复后引擎以普通权限运行（它本来也不需要特殊权限）。

**支持的构建与 sha256 门禁**：

| 构建（驱动版本） | 原版 | 打补丁后 | 修复后 |
| --- | --- | --- | --- |
| 26.20.29.02（2026-11，当前） | `3f1f9ce1…1dbe848c` | `0863b4d6…3b4fa564` | `1f59bc9a…0dea3311` |
| 26.20.15.16（2026-11） | `5808eed2…4fbbb6d5` | `0d8379ce…2707a883` | `c726d431…9b7fe404` |
| 26.20.15.12（2026-11） | `463724dd…95bdadf` | `4804a207…fff11c4a` | `10f3a904…76993e2b1` |
| 26.20.15.07（2026-10） | `ff26b09a…6fc3528` | `0dc22efa…30447e` | `ae4f3058…1aa66156e` |
| 26.20.15.02（2026-09） | `0f28b308…d5e450c9` | `1ae3fcc5…8194ba` | `72099cb6…7a5f840` |

`.02` 与 `.07` 等长（2628872 字节），`.12` 为 2628880 字节（多出的 8 字节全在文件末尾签名区，均为 `00` 填充），`.16` 为 2627480 字节（签名区缩小 1400 字节）——这四代七个节区的 off/size/va 完全一致，代码段未动，补丁点、函数帧与清单位置也完全一致；`.02`→`.07` 的逐字节差异仅 0.05%（版本串与签名哈希）。可以说前四代 AMD 并未修复该处代码，只是把打过补丁的文件整体替换。

`.29.02` 是首次真正的代码变化：文件 2670488 字节（比 `.16` 大 3008），节区表重排，类名长度补丁点由 `0x3686B` 漂移到 **`0x3669B`**——目标指令序列与上下文指纹仍然唯一，只是位置变了；清单位置也由 `0x27C03C` 移到 `0x28683c`。因此脚本不再把偏移量写死在代码里：所有构建数据（大小、三元哈希、补丁点、结构指纹）都收进 `build_manifest.json`，脚本只按 sha256 查表。适配新版本＝在清单里新增一条构建记录，无需改脚本；清单未登记的文件会被拒绝（见第八节）。

所有脚本带 **sha256 门禁**：文件状态与目标构建不符（如 AMD 已更新程序）时明确拒绝动作，不会乱改。

## 四、环境与兼容性

- 实测环境：Windows 11 + AMD Software: Adrenalin Edition，驱动 **26.20.29.02 / 26.20.15.16 / .12 / .07 / .02** 五代均已实测；RX 7900 XT（RDNA3）。
- 依赖：PowerShell 5.1+（改写系统文件的脚本自动请求 UAC 提权）；Python 3.8+ 且 **`pefile` 必需**——安装命令与验证方式见文首「使用前必装」。
  入口选解释器的顺序：PATH 上的 `python` / `py` / `python3` → 常见用户级安装路径（`%LOCALAPPDATA%\Programs\Python\Python*`、`…\binaries\python\versions\*`、`…\envs\default\Scripts`），**逐个试跑 `import pefile`，第一个成功的才采用**；全都不可用时列出每个候选的失败原因并中止，不会带着缺依赖的解释器往下跑。想手动指定就设环境变量 `DVR_TOOLKIT_PYTHON=<python.exe 路径>`。
- 脚本按 sha256 精确识别文件状态与构建代际（清单内置 **26.20.29.02 / 26.20.15.02 / .07 / .12 / .16** 五代），**只对已验证的构建生效**；AMD 更新 `AMDRSServ.exe` 后补丁会失效，需重新适配（见第八节）。
- 其他 AMD 版本不一定适用；不适配时脚本会中止并说明，不会强行修改。

## 五、快速上手：按场景选

| 场景 | 双击哪个 |
| --- | --- |
| 点录制没反应（静默失败） | **第一步先双击 `重启引擎和界面.cmd`**（启动方式缺陷：直启界面缺 `cncmd watch` 控制通道，最常见、约 40 秒、无副作用、不需管理员）；仍不行再按第九节判据分辨：A（补丁失效）→ **注入引擎修复补丁.cmd**；B（音频僵死）→ 关掉麦克风录制 |
| AMD 驱动或软件更新后（修复被覆盖） | **注入引擎修复补丁.cmd**（需 `pefile`，见文首「使用前必装」） |
| 想彻底回到官方原版 | **恢复原版.cmd** |
| DVR 日志太多占地方 | **清理DVR日志.cmd** |
| 想开 / 关 DVR 日志（排查取证用） | **切换DVR日志开关.cmd** |

涉及系统文件改写的脚本（`注入引擎修复补丁` / `恢复原版`）会请求管理员权限，UAC 点「是」；
`重启引擎和界面` **不需要管理员**，只关进程、不改文件。

> **两个入口不是必须连续执行的一对，别按名字字面顺序理解**
> `注入引擎修复补丁` = 改文件、一次性（首次使用 / AMD 更新后 / 日志出现 `Failed to send scene conversion`），做完必须重启电脑；
> `重启引擎和界面` = 只重启进程、按正确方式拉起界面（`cncmd startwithdelay` + `watch`），**点录制没反应时的第一反应**，随时可跑、反复跑无害。
> 日常排障请按「先重启引擎和界面、后注入引擎修复补丁」的成本顺序来。

## 六、首次使用顺序（重要）

1. 双击 **注入引擎修复补丁.cmd**（UAC 点「是」）：首次运行会在 `backup\` 自动创建官方原版备份（sha256 校验），随后打补丁 + 修清单（uiAccess true→false），经临时计划任务以普通权限重启引擎并校验存活；失败自动回滚。幂等：已修复则跳过。
2. **重启电脑**，再点一次录制验收（见第十节：不重启时引擎可能带管理员令牌，录制仍会失败）。
3. 重启后若点录制仍毫无反应（按钮可点但无任何效果，日志没有 `Failed`）→ 双击 **重启引擎和界面.cmd**（界面启动方式缺陷：直启缺 `cncmd watch` 控制通道，见第九节 D 组），再试录，通常无需再重启。

> `backup\` 已在 `.gitignore` 中——AMD 官方原版二进制不随仓库分发（版权与体积原因），首次运行时自动生成，**不要删除**。

## 八、AMD 更新之后

驱动/软件更新会替换 `AMDRSServ.exe`，补丁与清单修改一起失效：

- 重跑「注入引擎修复补丁.cmd」重新打上，**然后重启电脑再测试**（脚本重启的引擎带管理员令牌，该形态下录制不会好）。
- 若提示「状态不符」，说明文件已换成新构建（清单里没有对应记录）——**不要强行操作**。适配现在是**纯清单操作**：① 在 `backup\` 存一份新版原版并登记 `backup_info.txt`；② 在 `build_manifest.json` 的 `builds` 新增一条（orig / patched / fixed 三哈希；若补丁点漂移再加 `patch_points` 覆盖，`26.20.29.02` 即范例）。**不再需要改 `patch_manifest.py` / `restore_original.ps1`**。偏移量默认沿用规则值（`.02`–`.16` 四次均未变；`.12` 曾长 8 字节、`.16` 又短 1400 字节，增量全在签名区；`.29.02` 增大 3008 字节且补丁点漂移，属首次代码变化）。

## 九、怎么判断「又坏了」

⚠ **先看有没有 dvrlog**：门控分两代——旧代（≤ 26.20.15.x）看 `HKCU\SOFTWARE\AMD\DVR` 的 `LOG` **值**（存在即写，`=1`/`=0` 都写）；新代（≥ 26.20.29.02）看 `HKCU\SOFTWARE\AMD\DVR\LOG` **子键**的 `log_enabled`（`1` 写 / `0` 停，旧值完全失效）。用「切换DVR日志开关.cmd」开关即可，它对两处同时写入，不必自己分辨驱动属于哪一代。
没有日志时无法直接区分成因，按**成本从低到高**盲排：① 先双击「重启引擎和界面.cmd」→ 试录；② 仍不行 → 关掉麦克风录制 → 立刻试录；③ 仍不行 → 重跑「注入引擎修复补丁.cmd」→ **重启电脑** → 试录。最终判据始终是**实际录制落盘**，错误数 0、界面无提示都不算数。

有日志时，先点一次录制，看有没有文件落盘。没反应时，按最新 dvrlog 的特征查，命中即停：

| # | 判据（最新 dvrlog） | 成因 | 处置 |
| --- | --- | --- | --- |
| A | 有 `Failed to send scene conversion to CN` | 类名读取越界（本工具包修的那个） | 补丁失效 → 重跑「注入引擎修复补丁.cmd」→ **重启电脑** |
| B | **完全没有** `WMCN_` 开头的行、也没有 `Failed`，且麦克风录制开着、有 `AMF_FILE_NOT_OPEN` | 引擎已僵死（音频枚举失败），录制请求根本没发出去 | 见下方 B 组 |
| C | 有 `SCENE_CONVERSION_DONE` 但没落盘 | 编码器 / 磁盘 / 开关问题 | 查输出目录、编码器设置 |
| D | 没有 `WMCN_` / `Failed`，但引擎**看起来正常**（有 `Instant replay has been started`、日志持续在刷），**连杀引擎也无效** | 界面与引擎的控制通道没建立：最常见是界面**未经 `cncmd startwithdelay` 启动**（直启 `RadeonSoftware.exe`，或被杀后由非标准方式拉起），缺 `cncmd watch <pid>` 子进程 → 界面「按钮能点、点了不发命令」 | 双击「重启引擎和界面.cmd」；完成后界面停在托盘即可用（双击托盘打开是中文界面），**不要直接启动 `RadeonSoftware.exe`，也不要用 `cncmd show`**（会把界面切成英文） |

**B 与 D 怎么分**：两者日志都「干净」。B 的麦克风录制开着且有关键错误 `AMF_FILE_NOT_OPEN`，关麦即恢复；D 的引擎本身健康、关麦无效，**只有把界面和引擎一起按顺序重来才恢复**。

**B 组：`AMF_FILE_NOT_OPEN` 的双重语义（别一概当噪声）**

同一句 `AMF_FILE_NOT_OPEN: Open() failed` 有两种含义，靠麦克风录制是否开启区分：

- **麦克风录制关闭**（`HKCU\SOFTWARE\AMD\DVR\AudioInputCaptureEnabled = 0`）：即时重放的常态噪声，出现在 `Instant replay has been started` 之前，不影响录制。
- **麦克风录制开启**（`= 1`）且音频设备枚举异常：`MicFileOutput` 打开失败 → **引擎僵死** → 此后所有桌面录制被静默拒绝（日志 0 条 `WMCN_`），点录制完全无反应。

处置：在 AMD 软件里关掉「麦克风」录制（或换一个可枚举的设备）→ 立即试录，**无需重启**（实测关麦后数秒内出现 `SCENE_CONVERSION_DONE`）。若不需要开麦，建议长期保持关闭——开着它每次冷启动都可能再僵死一次，且症状与 A 组完全相同、极易误判。

## 十、已知现象（重要）

1. **修复后必须重启电脑再测试录制。** 修复脚本通过提权会话重启引擎时，引擎可能带上管理员令牌；实测该形态下录制**仍然失败**（2026-10-23：文件已确认修复、点击录制仍无反应、零落盘；重启电脑后引擎以普通权限拉起，一次成功、正常落盘）。重启后引擎会自动恢复普通权限形态。
   - 附带现象：管理员形态引擎写的 dvrlog 用普通权限读不到，此时无法取证。
2. 若脚本重启过 AMD 界面，**界面语言可能变成英文**——重开界面或重启电脑会自动恢复中文，所有设置不会丢。
3. 桌面录制开关由你在 AMD 软件里控制。关着时点录制，AMD 会弹窗提示开启，属正常流程。
4. **若不需要麦克风录制，建议保持关闭**——麦克风开启且音频设备不可枚举时，引擎会在冷启动后僵死（第九节 B 组），症状与补丁失效完全一样，极易误判。
5. **「界面半瘫」来自启动方式，不是补丁问题、也不是竞态**（2026-11-23 实证）：界面必须经 `cncmd startwithdelay` 启动、并带一个 `cncmd watch <pid>` 子进程，才算与 DVR 引擎建立了控制通道（watch 分支内部执行 `RSServCmd.exe make dvr hide_ui`）。直接运行 `RadeonSoftware.exe` 会得到一个「按钮可点、点下去引擎零请求」的半瘫实例，杀引擎也救不回来（第九节 D 组）。处置：双击 **重启引擎和界面.cmd**——它先关界面、再关引擎，等守护进程把引擎拉回来后经 `cncmd startwithdelay` 重新拉起界面；**界面停在托盘就是已就绪**（托盘态主窗口本就不存在，不要等窗口出现）。需要看界面时双击托盘图标打开（这样打开是中文），不要用 `cncmd show`。

3. 本工具与 AMD 无任何关联；按「原样」提供，使用需自担风险。
